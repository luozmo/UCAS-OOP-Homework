# ChampSim 微架构模拟器的自身优化设计
## 面向对象程序设计课程大作业选题大纲（草稿）

> 选题定位：以 ChampSim 模拟器为真实软件系统，优化其“仿真框架自身”的运行时性能、内存占用或可扩展性，而不是只替换一个缓存参数或引用现成预取器。除非某个子方向明确要改变微架构策略，否则优化前后必须保持被模拟系统的行为与统计结果一致。

---

## 1. 项目背景与课程目标

### 1.1 系统背景

ChampSim 是一个基于 trace 的微架构模拟器，通过逐周期推进处理器核心、缓存、页表遍历器和 DRAM 控制器等对象，模拟乱序处理器和存储层次的行为。主要语言为 C++，源码中已经具有较清晰的对象和接口层次，适合进行面向对象分析、设计与优化。

### 1.2 选题目标

本选题研究 ChampSim 自身在以下一个或多个方面的优化：

1. 降低模拟器主机侧（host-side）运行时间和每模拟周期开销。
2. 降低大规模配置下的峰值内存占用和动态内存分配次数。
3. 改善对象调度、数据流和统计管线，使其更易测试、扩展和复现实验。
4. 在不改变模拟语义的前提下，验证优化是否具有稳定、可解释的实际效果。

由于课程大作业要求选择“一个具体方向”，建议优先从第 3 节中选择一个主方向。其余方向可作为同一方向下的二次优化，或作为最终报告中的“未采用方案与原因”。

### 1.3 与课程要求的对应关系

| 课程要求 | 本项目对应内容 |
| --- | --- |
| 系统理解 | 分析配置、对象图构建、逐周期推进、缓存访问、trace 输入和统计输出流程 |
| 需求分析与建模 | 定义“缩短运行时间且保持统计一致”等功能与非功能需求 |
| 对象职责与接口 | 分析 `operable`、`environment`、`CACHE`、`O3_CPU`、`channel`、`tracereader` 等对象 |
| 方案设计与实现 | 选择调度、内存或数据管线中的一个方向完成可运行改造 |
| 测试与效果验证 | 单元测试、回归测试、差分测试和性能基准测试 |
| 过程记录 | 记录 profiling 证据、方案迭代、失败尝试、基线偏差和修正过程 |

## 2. 系统理解与对象建模

### 2.1 核心对象

| 对象或模块 | 主要职责 | 与优化选题的关系 |
| --- | --- | --- |
| `champsim::environment` | 暴露 CPU、缓存、PTW、DRAM 和 `operable` 视图 | 视图对象的创建频率和生命周期影响调度开销 |
| `champsim::operable` | 统一时钟周期、初始化、逐周期操作和阶段生命周期 | 所有仿真组件的公共接口，是调度优化的核心 |
| `O3_CPU` | 前端取指、译码、分派、乱序执行和退休 | 主要仿真负载来源之一 |
| `CACHE` | 标签检查、MSHR、填充、写回、预取和替换 | 缓存包生命周期和分配行为影响内存与运行时间 |
| `PageTableWalker` | 多级页表遍历与地址翻译 | 多级存储配置下的重要组件 |
| `MEMORY_CONTROLLER` / `DRAM_CHANNEL` | DRAM 请求调度和时序模拟 | 与缓存热路径共同构成内存侧主要开销 |
| `champsim::channel` | 保存 RQ、PQ、WQ，传递请求与响应 | 存在整包复制、队列增长和依赖向量复制等优化空间 |
| `champsim::tracereader` | 从不同格式和压缩流读取、批处理 trace | 影响 trace 解码、缓冲、复制和输入管线开销 |
| 模块接口 | 分支预测、BTB、预取器和替换策略 | 可观察策略与框架接口的关系，不作为首选的纯参数调优对象 |
| `core_builder` / `cache_builder` | 根据配置构造核心和缓存对象 | 对象图构建、模板实例和接口约束的入口 |
| `phase_stats` 与 printer | 阶段边界汇总并输出文本或 JSON 统计 | 阶段切换存在对象复制，影响长仿真和测试管线 |
| 事件监听器 | 在阶段事件发生时触发处理 | 可用于解耦观测逻辑与仿真主循环 |

### 2.2 核心执行流程

```text
JSON 配置
  -> config.sh 解析与代码生成
  -> generated_environment 构造 channels / DRAM / PTW / CACHE / CPU 对象
  -> initialize()
  -> 对每个 phase 执行 begin_phase()
  -> 每个最小时钟步：
       推进 global_clock
       -> 取得 operable 视图并排序
       -> 依次执行 operable::operate_on()
       -> 从 trace 补充 CPU 输入队列
       -> 检查阶段完成和异常
  -> end_phase()
  -> 汇总 CPU / CACHE / DRAM 统计
  -> plain_printer / json_printer 输出
```

### 2.3 需要先用实验确认的现象或假设

以下内容是代码阅读后形成的优化假设，不能直接当作结论，必须先通过 profiling 验证：

1. `src/champsim.cc` 的 `do_cycle()` 每周期调用 `env.operable_view()`，随后对视图排序；在对象数量较大时，这会带来重复容器构造、引用复制和排序开销。
2. `inc/operable.h` 和 `src/operable.cc` 通过虚函数完成组件的逐周期操作；对象数量和周期数增大后，动态分派成本需要量化。
3. `src/channel.cc` 的 `do_add_queue()` 对请求包进行复制，而请求/响应中含 `std::vector` 依赖信息；高频传输时需要评估分配和复制成本。
4. `src/cache.cc` 在 MSHR、填充、响应和依赖集合之间进行多次值复制；需要区分必要的数据所有权转移与非必要拷贝。
5. `inc/tracereader.h` 的批量 trace 读取会经历压缩流、原始缓冲、trace 结构和核心指令模型等多个阶段；需要判断 trace 输入是否为主要瓶颈。
6. `src/champsim.cc` 在阶段结束时复制 CPU、缓存和 DRAM 统计对象；对长周期、多阶段实验，统计汇总路径需要测量。
7. `config.sh` 与 `config/instantiation_file.py` 会生成具体环境代码；模块数量和配置规模对编译时间及二进制体积的影响可以作为辅助指标。

### 2.4 必须保持的约束

- 固定 CPU、缓存、DRAM、trace、warmup 指令数和 simulation 指令数。
- 优化框架本身时，优化前后的 IPC、缓存命中/缺失、预取、DRAM 等统计结果应一致。
- 若研究方向会改变微架构策略，必须明确区分“模拟结果变化”和“模拟器运行速度变化”，并分别报告。
- 不把编译器优化等级变化当作唯一优化手段，必须说明代码和对象设计层面的改动。
- 不依赖手工修改生成文件；若涉及代码生成，应修改配置侧逻辑并重新生成。

## 3. 候选研究方向

### 3.1 方向 A（推荐）：仿真调度与时钟推进优化

#### 问题背景

ChampSim 的 `do_cycle()` 在每个最小时钟步取得全部 `operable` 对象，并按 `current_time` 排序后执行。对象图在初始化后基本固定，因此可以研究是否将“视图构造、排序和访问”转为稳定注册的调度结构。

#### 目标

在保持仿真顺序和结果一致的前提下，降低每个模拟周期的调度开销，提升整体 wall-clock 性能。

#### 主要挑战

- 不同 `operable` 可能具有不同时钟周期，不能简单改成固定顺序。
- 相同 `current_time` 下必须保持确定的执行顺序，否则可能改变碰撞结果。
- `environment`、生成代码和 `operable` 接口之间需要明确职责，避免把调度知识散落在各组件中。
- 缓存排序结果或增量维护顺序时，必须证明其与基线的执行语义一致。

#### 建议设计位置

- 新增独立的 `simulation_scheduler` 或等价职责对象，负责注册、稳定排序和推进消费。
- `environment` 只提供稳定注册信息，不在每个周期重复构造大规模视图。
- 保留 `operable` 的最小公共协议；将调度策略作为单独的职责，而不是塞入 `O3_CPU` 或 `CACHE`。
- 对同周期对象使用稳定序号或稳定排序，明确并列项的确定性规则。

#### 最小可交付版本

- 支持不同时钟周期的混合组件并保持结果一致。
- 调度器的单元测试覆盖：周期相同、周期不同、注册顺序变化、阶段切换。
- 与基线运行相同的 trace，对比文本统计和 JSON 统计。
- 至少给出 profiler 证据，说明优化命中真实热点，而非只凭代码猜测。

#### 验证指标

- 主指标：总 wall-clock 时间、每 retire 指令的 host 时间、每模拟周期 host 时间。
- 辅助指标：峰值 RSS、动态分配次数、指令数、缓存缺失等。
- 正确性门禁：模型统计完全一致；重复运行结果稳定。

#### 不采用的方案示例

“直接删除排序”可能改变同周期对象的执行顺序，不能采用；必须通过稳定顺序、增量调度或其他等价机制保持语义。

### 3.2 方向 B：缓存与通道热路径的对象生命周期优化

#### 问题背景

缓存请求、响应、MSHR、依赖列表和返回队列之间存在较多的值复制。对象复制不仅消耗 CPU，还可能造成频繁堆分配，尤其在高频访存和大会话仿真中更为明显。

#### 目标

通过更明确的所有权、移动语义、容量预留和队列数据布局，降低主机侧运行时间和峰值内存占用，同时不改变请求顺序和依赖语义。

#### 主要挑战

- `instr_depend_on_me` 和 `to_return` 等字段可能被多个阶段引用或合并。
- 简单改成指针或引用容易出现悬空指针和生命周期错误。
- 必须区分“正常合并”与“重复复制”，不能为了减少拷贝而改变 MSHR 合并逻辑。
- 优化后的队列行为必须覆盖满队列、合并、翻译、写回和预取路径。

#### 建议设计位置

- 为请求包建立清晰的值语义或所有权语义，明确创建者、消费者和生命周期。
- 在 `channel` 中区分只读传递与所有权转移接口，避免每次入队都无差别复制。
- 对确实需要保留的依赖集合使用预留、移动或更紧凑的数据结构，并记录选择依据。
- 通过适配层隔离缓存逻辑和底层容器细节，避免各模块直接依赖具体容器实现。

#### 最小可交付版本

- 选择一个高频且可复现的缓存/访存场景完成优化。
- 保持 RQ、PQ、WQ 的先进先出和满队列判断一致。
- 对请求合并、依赖回传、翻译和预取路径增加或补充测试。
- 与基线比较运行时间、峰值 RSS 和分配次数。

#### 验证指标

- 主指标：总运行时间、访存密集 trace 的运行时间。
- 辅助指标：峰值 RSS、堆分配次数、缓存相关统计。
- 正确性门禁：请求顺序、命中/缺失、MSHR 合并、填充和预取统计一致。

### 3.3 方向 C：Trace 输入与统计输出管线优化

#### 问题背景

trace 读取经过压缩流、缓冲、格式转换和分支目标修正等多个阶段；仿真结束后还需要复制和汇总 CPU、缓存和 DRAM 统计。对于短配置、多阶段或大量重复实验，这部分开销不一定可以忽略。

#### 目标

降低 trace 输入和统计输出对总仿真时间的影响，并改善这两条管线的接口清晰度和可测试性。

#### 主要挑战

- trace 格式、压缩格式和 cloudsuite 模式存在多种组合。
- 统计输出既要保持文本格式，又要保持 JSON 字段兼容。
- 如果使用异步或批量处理，必须保证输入顺序与错误处理语义一致。
- 优化效果可能被核心仿真主导，需要通过 short-trace 或统计密集场景证明收益。

#### 建议设计位置

- 明确 trace source、解码器、批缓冲和指令构造之间的职责边界。
- 统计侧引入采集、聚合和输出职责分离，避免 printer 直接承担所有格式逻辑。
- 通过事件或阶段监听器观察统计，减少阶段边界上的整体复制。
- 保持文本与 JSON 输出兼容，便于差分测试。

#### 最小可交付版本

- 至少覆盖 gzip、xz 与未压缩 trace 中的两类输入。
- 对比短 trace、多阶段和重复实验场景的运行时间。
- 验证文本输出与 JSON 输出字段、数值和顺序符合预期。
- 提供统计格式的回归测试。

#### 验证指标

- 主指标：trace 读取吞吐量、统计阶段耗时、实验总时间。
- 辅助指标：峰值 RSS、JSON 文件大小、对象复制次数。
- 正确性门禁：输入指令序列和所有输出统计一致。

### 3.4 方向 D（可选）：配置生成与模块构建优化

如果课程更强调“面向对象设计和工程可维护性”，可研究配置到对象图的生成过程：

- 分析 `config/instantiation_file.py`、`core_builder`、`cache_builder` 和模块类型擦除机制。
- 减少重复模板实例、过长编译时间和不必要的头文件耦合。
- 改善模块接口的扩展方式，使新策略更容易接入、测试和验证。
- 以配置时间、增量编译时间、完整编译时间和二进制体积作为量化指标。

该方向同样需要保证生成后的模拟语义不变，并补充配置解析和模块实例化测试。

## 4. 面向对象分析与设计要求

### 4.1 必做模型

1. **用例模型**：研究者运行基线仿真、启动优化版本、比较统计、复现实验。
2. **领域对象模型**：说明对象、属性、职责、关系和生命周期。
3. **类图**：至少覆盖 `environment`、`operable`、一个仿真组件、调度器和统计输出对象。
4. **时序图**：至少覆盖一次完整的“时钟推进 -> 组件操作 -> 状态更新 -> 阶段统计”流程。
5. **接口契约**：列出输入、输出、前置条件、后置条件、异常和所有权规则。
6. **设计决策记录**：说明采用某方案的原因、替代方案和未采用原因。

### 4.2 可使用的设计思想

| 设计思想 | 适合处理的职责 | 使用注意 |
| --- | --- | --- |
| Builder | 从配置构造对象图 | 不应把模拟行为藏进 builder |
| Strategy / Policy | 替换调度、队列或统计策略 | 必须说明与现有模板模块接口的边界 |
| Facade | `environment` 对外提供统一视图 | 不应因 facade 隐藏关键生命周期问题 |
| Observer | 阶段事件和统计监听 | 注意事件顺序和观察开销 |
| Adapter | 兼容已有模块或旧数据格式 | 适配层不应改变原语义 |
| Pipeline | trace 输入或统计输出 | 关注背压、顺序和异常传播 |
| Value Object / RAII | 请求包、缓冲区、统计对象 | 明确拷贝、移动和所有权，避免悬空引用 |

设计模式不是评分点本身。报告中必须说明“为什么需要该职责分离”，而不是为了使用模式而增加抽象层。

## 5. 实验设计

### 5.1 基线

- 使用原始 ChampSim 代码构建并保存基线二进制。
- 记录编译器版本、构建命令、CPU 型号、内存容量、操作系统和调度设置。
- 固定 `champsim_config.json`、trace 文件、warmup 和 simulation 指令数。
- 如果有多套配置，至少保留默认单核配置和一套多核/多级缓存配置。

### 5.2 基准 trace

建议至少选择 5 条具有不同访存行为的 trace，覆盖：

1. 计算密集；
2. 分支密集；
3. L1/L2 访存密集；
4. 预取敏感；
5. DRAM 带宽受限；
6. 可选：多核共享 LLC 或地址翻译密集场景。

若 trace 资源有限，可减少到 3 条，但必须说明选择理由，不能只使用对优化最有利的一条。

### 5.3 对比方案

至少包含：

- 原始基线；
- 完整优化版本；
- 至少一个消融版本，例如只优化调度、只优化队列或只优化 trace；
- 如果时间允许，增加一个替代设计版本，用于解释设计取舍。

### 5.4 指标

- 运行时间：总时间和按 trace 时间；
- 主机效率：每模拟周期时间、每百万 retire 指令时间；
- 内存：峰值 RSS、分配次数、堆占用；
- 正确性：IPC、缓存、预取、DRAM、阶段统计；
- 工程质量：编译时间、二进制体积、测试覆盖范围、重复运行稳定性。

建议每个配置重复运行不少于 5 次，报告均值、中位数和波动范围；性能结论不能只基于一次运行。

### 5.5 建议验收标准

以下阈值是示例，最终应结合时间和机器资源调整：

- 正确性：不改变微架构策略时，主要统计结果必须一致，重复运行无随机偏差。
- 性能：在至少 3 条代表性 trace 上取得稳定提升，整体中位数提升不小于 8% 至 10%。
- 内存：内存优化方向在访存密集场景中显著降低峰值 RSS 或分配次数。
- 工程质量：所有新增接口具有单元测试，`make test` 与关键集成测试通过。
- 可解释性：能用 profiling 结果说明瓶颈位置、优化命中的路径以及剩余瓶颈。

### 5.6 测试方案

1. **单元测试**：调度顺序、混合时钟周期、队列满/空状态、移动语义和统计聚合。
2. **差分测试**：比较基线版与优化版的 JSON 输出，忽略仅与主机时间有关的字段。
3. **回归测试**：覆盖缓存合并、MSHR、翻译、预取、写回和阶段切分。
4. **压力测试**：多核、多级缓存、长 trace、队列接近满载和 trace 结束边界。
5. **工具验证**：使用 `make test`、Python 测试、ASan/UBSan 或等价手段检查生命周期问题。
6. **性能验证**：使用 `perf`、VTune、`/usr/bin/time -v`、Massif 或其他可行工具留存证据。

## 10. 风险与规避

| 风险 | 影响 | 规避方式 |
| --- | --- | --- |
| 选题过大 | 无法在学期内完成 | 只选一个主方向，其他方向只做分析 |
| 把主机性能变化误认为微架构性能变化 | 结论错误 | 分开报告 host wall-clock 与模拟器统计 |
| 优化改变对象执行顺序 | 统计不可复现 | 差分测试、稳定排序和固定随机种子 |
| 只做局部微优化 | 收益不稳定 | 先用 profiling 找热点，再确定改动 |
| 只测一条 trace | 结论泛化性差 | 至少 3 条、最好 5 条不同负载 |
| 只保留成功方案 | 不符合课程过程要求 | 记录失败尝试、回退和原因 |

# 基于 ChampSim 的实验结果采集、并行编排与可视化子系统
## 面向对象程序设计课程大作业方向大纲

> 方向定位：围绕 ChampSim 增加一套面向微架构研究的实验基础设施，统一完成“实验定义、并行运行、原始结果归档、结构化解析、指标计算、方案对比和图表演示”。该方向属于课程说明中的“需求驱动的系统扩展 / 模块开发”，不是单纯写脚本画图，也不是只替换一个缓存或预取器参数。

---

## 1. 项目背景

### 1.1 现有情况

ChampSim 可以运行不同 trace，并通过配置选择不同的预取器、替换策略和系统参数。当前已经具备一些基础输出能力：

- `cache_stats` 中包含 `pf_requested`、`pf_issued`、`pf_useful`、`pf_useless` 等预取统计。
- `json_printer` 可以将 CPU、缓存和 DRAM 的阶段统计输出为 JSON。
- 预取器、替换策略等模块具有初始化、运行和最终统计钩子。
- 运行方式主要以单次命令行为主，一次运行对应一条 trace 和一套配置。

### 1.2 主要问题

面向硬件方向做研究时，实验通常具有以下特点：

1. 需要同时比较多个预取器、多条 trace 和多套缓存配置。
2. 需要重复运行多次，分析均值、中位数、方差和异常样本。
3. 文本输出和单次 JSON 文件不便于直接形成统一比较结果。
4. 某些研究指标没有现成输出，需要在仿真过程中增加埋点。
5. 手工运行和手工整理图表容易产生配置不一致、结果覆盖和不可复现问题。
6. 现有预取器的自定义统计可能只打印到屏幕，不能稳定参与后续自动分析。

### 1.3 项目目标

构建一套可运行的实验平台子系统，使其能够：

- 用统一的实验描述定义多个预取器、trace、配置和重复次数。
- 以受控并行方式运行多个独立仿真任务。
- 保存每次运行的命令、配置、日志、原始统计和运行状态。
- 将原始结果解析为统一的对象模型。
- 从已有统计中派生指标，并通过扩展点记录新增指标。
- 支持与基线方案比较，生成表格、图表和实验报告。
- 保证结果可复现、可追踪、可测试和可扩展。

### 1.4 与课程要求的对应

| 课程要求 | 本项目中的体现 |
| --- | --- |
| 系统理解 | 理解 ChampSim 运行方式、统计输出、预取器接口和阶段统计 |
| 需求分析 | 分析批量实验、公平比较、缺失指标和自动绘图需求 |
| 对象建模 | 建立实验、任务、原始结果、指标、比较结果和图表对象 |
| 核心流程设计 | 设计“定义 -> 调度 -> 运行 -> 解析 -> 计算 -> 对比 -> 渲染”流程 |
| 模块开发 | 实现实验编排、结果解析、指标注册和可视化模块 |
| 配套测试 | 单元测试、模拟执行器测试、解析回归和端到端小实验 |
| 效果验证 | 验证并发执行、结果一致性、指标正确性和图表可读性 |

## 2. 选题范围与边界

### 2.1 建议纳入范围

- 实验配置和任务矩阵。
- 进程级并行运行和资源限制。
- 运行状态、日志和原始结果归档。
- 结构化解析和统一结果模型。
- 现有指标的派生计算。
- 少量新增指标的仿真侧埋点。
- 基线比较和统计汇总。
- 静态图表、表格和 HTML/Markdown 报告。
- 测试和复现实验说明。

### 2.2 建议排除范围

为了控制课程项目规模，第一版不建议包含：

- 完整图形化桌面应用或复杂在线数据库。
- 分布式集群调度器。
- 自动推断研究方向或自动生成论文结论。
- 支持所有历史版本 ChampSim 的全部输出格式。
- 无边界插件市场或脚本执行平台。
- 在同一个缓存中同时运行多个预取器并直接当作公平性能比较。

如果研究内容确实需要多个预取器同时作用于一个缓存，应把它定义为“预取器交互研究”，不能与单预取器独立运行结果混在一起解释。

## 3. 总体数据流

```text
ExperimentSpec
    |
    v
JobPlanner ----------> RunSpec[]
    |                       |
    |                       v
    |              ParallelRunScheduler
    |                       |
    |                       v
    |                  RunExecutor
    |                       |
    |                       v
    |                  RunArtifact
    |                       |
    |                       v
    |                  ResultParser
    |                       |
    |                       v
    +----------------> RunResult / ResultSet
                            |
              +-------------+-------------+
              |                           |
              v                           v
       MetricRegistry                 Comparator
              |                           |
              +-------------+-------------+
                            |
                            v
                        ChartSpec
                            |
                            v
                    Renderer / ReportBuilder
```

核心原则：

- 实验编排不负责解析和绘图。
- 解析器不负责启动进程。
- 指标定义不依赖具体图表库。
- 渲染器不直接访问 ChampSim 内部对象。
- 所有层通过稳定的结果模型和接口协作。

## 4. 核心对象与职责

### 4.1 实验定义层

| 对象 | 职责 |
| --- | --- |
| `ExperimentSpec` | 描述整个实验，包括名称、基线、trace 集合、预取器集合、重复次数 |
| `TraceSpec` | 描述 trace 路径、格式、warmup 和 simulation 指令数 |
| `PrefetcherSpec` | 描述预取器名称、参数和配置来源 |
| `CacheConfigSpec` | 描述 L1/L2/LLC 等配置 |
| `RunSpec` | 描述一次确定的仿真实验，具有唯一 ID |
| `ExperimentId` / `RunId` | 为结果追踪提供稳定标识 |

`ExperimentSpec` 和 `RunSpec` 应尽量保持不可变。实验开始后修改运行参数，会使结果无法追踪。

### 4.2 调度与执行层

| 对象 | 职责 |
| --- | --- |
| `JobPlanner` | 将实验矩阵展开为多个 `RunSpec` |
| `ParallelRunScheduler` | 控制并发度、排队、取消、超时和失败重试 |
| `ResourcePolicy` | 描述最大并行任务数、CPU 关联或内存限制 |
| `RunExecutor` | 启动 ChampSim 进程并等待结束 |
| `RunWorkspace` | 管理单次运行的独立目录和输出文件 |
| `RunArtifact` | 保存原始 stdout、stderr、JSON、日志和运行元数据 |
| `RunState` | 表示任务的生命周期状态 |

任务状态可以采用：

```text
CREATED
  -> QUEUED
  -> RUNNING
  -> SUCCEEDED / FAILED / TIMED_OUT / CANCELLED
  -> PARSED
  -> VALIDATED
```

并行执行建议采用**一任务一进程**：

```text
(预取器, trace, 配置, 重复编号) -> 一个独立 ChampSim 进程
```

这样可以隔离全局状态、工作目录和输出文件，避免在模拟器内部引入多线程共享状态问题。

### 4.3 结果解析层

| 对象 | 职责 |
| --- | --- |
| `ResultParser` | 将原始输出转换为结构化 `RunResult` |
| `JsonResultParser` | 解析 ChampSim JSON 输出 |
| `LegacyTextParser` | 在必要时兼容文本输出 |
| `RunResult` | 表示一次运行的核心统计和元数据 |
| `ResultSet` | 按 trace、预取器、配置等维度组织多次运行结果 |
| `SchemaValidator` | 校验字段、单位、阶段和版本 |

解析器应该优先消费结构化 JSON，而不是从屏幕文本中使用正则表达式抓取数据。

### 4.4 指标与分析层

| 对象 | 职责 |
| --- | --- |
| `MetricDefinition` | 定义指标 ID、名称、单位、公式和优劣方向 |
| `MetricRegistry` | 注册已有指标和新增指标 |
| `MetricCalculator` | 从 `RunResult` 计算派生指标 |
| `Aggregator` | 计算均值、中位数、标准差、置信区间 |
| `BaselineSelector` | 选择比较基线 |
| `Comparator` | 计算增量、变化率和加速比 |
| `ComparisonResult` | 保存结构化比较结果 |

### 4.5 可视化与报告层

| 对象 | 职责 |
| --- | --- |
| `ChartSpec` | 描述数据来源、分组维度、坐标轴和图形类型 |
| `Renderer` | 渲染器的抽象接口 |
| `BarChartRenderer` | 生成预取器对比柱状图 |
| `LineChartRenderer` | 生成 trace 或参数变化折线图 |
| `HeatmapRenderer` | 生成预取器-trace 指标热力图 |
| `TableRenderer` | 生成 Markdown、CSV 或 HTML 表格 |
| `ReportBuilder` | 组合实验结果、表格、图表和说明 |
| `ArtifactStore` | 管理最终图表和报告的保存位置 |

`ChartSpec` 只表达“要展示什么”，具体图形库属于 `Renderer` 的实现细节。

## 5. 多态与扩展点设计

建议为以下接口定义抽象基类或协议：

```text
RunExecutor
ResultParser
MetricDefinition
Renderer
ArtifactStore
```

这样可以实现：

- 新增本地执行器或容器执行器，不修改调度器。
- 新增 ChampSim JSON 格式解析器，不修改指标计算。
- 新增指标，不修改比较器和绘图器。
- 新增 HTML、SVG 或 PNG 渲染器，不修改结果对象。
- 替换文件存储为实验数据库，不影响上层分析流程。

面向对象设计重点不是类越多越好，而是：

- 一个类只有一个清晰的职责。
- 接口的输入、输出和生命周期明确。
- 通过组合而不是深层继承复用行为。
- 新增功能主要通过新增实现类完成，而不是反复修改已有条件分支。

可以合理使用：

| 设计思想 | 用途 |
| --- | --- |
| Builder | 构造复杂实验配置 |
| Factory | 根据配置创建解析器、执行器或渲染器 |
| Strategy | 切换指标、解析和渲染策略 |
| Repository | 统一管理历史运行结果 |
| Adapter | 兼容不同 ChampSim 输出格式 |
| Observer | 通知任务状态变化和进度 |
| Template Method | 固定实验执行流程，允许子类替换步骤 |

## 6. 指标设计

### 6.1 可直接派生的指标

ChampSim 现有预取统计可以用于计算：

```text
预取准确率 = useful prefetch / issued prefetch
预取浪费率 = useless prefetch / issued prefetch
预取覆盖率 = useful prefetch / demand misses
预取请求有效率 = issued prefetch / requested prefetch
```

还可以计算：

```text
IPC = instructions / cycles
MPKI = cache misses / (instructions / 1000)
相对基线 IPC 变化率 = (IPC_variant - IPC_baseline) / IPC_baseline
实验加速比 = wall_time_baseline / wall_time_variant
```

所有指标必须注明：

- 来自 warmup 还是 ROI 统计；
- 统计对象是哪个缓存层级和 CPU；
- 分母是否包含某类访问；
- 是否包含预取请求；
- 多次运行时采用什么聚合方式。

### 6.2 需要新增埋点的指标

可以根据研究目标选择 1 至 3 个指标实现，例如：

| 指标 | 含义 | 可能需要的记录 |
| --- | --- | --- |
| 预取及时性 | 预取数据在 demand 到达前多久准备完成 | 预取发出、填充完成和 demand 到达时间 |
| 预取污染 | 预取填充是否挤出了后续会使用的行 | 预取来源、受害者地址、后续复用 |
| 预取队列占用 | 预取队列随时间的占用情况 | 每周期或事件采样 |
| MSHR 占用 | 预取造成的 MSHR 压力 | MSHR 插入、合并和释放 |
| 各层级命中收益 | 不同缓存层级上的预取收益 | 层级、访问类型和来源标记 |
| 带宽放大 | 预取增加的 DRAM 流量 | 预取请求、填充和 DRAM 事务计数 |

新增指标不应直接散落在多个 `std::cout` 语句中。建议设计统一的记录接口：

```text
StatRecord
- run_id
- metric_id
- scope
- value
- unit
- phase
- source
- schema_version
```

预取器的 `prefetcher_final_stats()` 可以作为最终统计钩子，但应优先输出结构化记录，而不是依赖屏幕文本解析。

### 6.3 指标注册信息

每个指标至少需要：

```text
metric_id
display_name
description
unit
scope
formula
higher_is_better
aggregation
source
version
```

例如：

```text
metric_id: prefetch_accuracy
display_name: 预取准确率
unit: ratio
higher_is_better: true
formula: pf_useful / pf_issued
source: derived
```

## 7. 并行运行设计

### 7.1 运行矩阵

建议第一版实验矩阵：

```text
预取器：no、next_line、ip_stride、spp_dev
trace：5 条，覆盖计算、分支、访存、预取和带宽场景
重复次数：3
并行度：1、4、8
```

如果时间有限，可缩减为：

```text
3 个预取器 × 3 条 trace × 3 次重复 = 27 个任务
```

### 7.2 公平比较要求

- 所有方案使用同一编译选项和同一 ChampSim 版本。
- trace、warmup 和 simulation 指令数一致。
- 除目标预取器外，缓存、DRAM、分支预测和替换策略一致。
- 每个任务在独立目录中运行，避免 JSON 和日志覆盖。
- 保存配置哈希、命令行、退出码、开始时间和结束时间。
- 失败任务不能静默忽略，必须进入最终报告。

### 7.3 并行正确性

同一组实验使用不同并行度运行时：

- 每个 `RunSpec` 的结果对象应一致；
- 排序后的统计结果应一致；
- 指标值应一致；
- 不能因为文件写入顺序不同而改变报告内容。

并行加速指标只表示实验吞吐率，不表示被模拟硬件性能。

## 8. 可视化设计

建议至少实现三类图：

1. **预取器对比柱状图**：IPC、准确率、覆盖率、MPKI。
2. **trace 对比折线图**：不同 trace 上各预取器的走势。
3. **预取器-trace 热力图**：快速观察最优和最差组合。
4. **箱线图或误差条图**：展示多次运行的波动范围。
5. **表格报告**：保留所有原始值、均值、变化率和失败任务。

推荐的输出形式：

```text
results/
  run_id/
    command.txt
    config.json
    stdout.log
    stderr.log
    result.json
    metadata.json
  summary.csv
  comparison.json
  report.html
  figures/
    ipc_bar.png
    prefetch_accuracy.png
    trace_heatmap.png
```

渲染层应消费 `ResultSet` 和 `ComparisonResult`，不直接读取原始日志。

## 9. 测试与验证

### 9.1 单元测试

- `JobPlanner`：实验矩阵展开是否正确。
- `ParallelRunScheduler`：并发上限、取消、超时和失败重试。
- `ResultParser`：正常输出、缺失字段、非法 JSON 和版本差异。
- `MetricCalculator`：公式、除零和聚合方式。
- `Comparator`：基线、增量和加速比。
- `Renderer`：输入对象到输出文件的映射。

### 9.2 模拟测试

使用假的 `RunExecutor` 或固定 JSON 文件模拟 ChampSim：

- 不实际启动仿真也能验证调度、解析和报告流程。
- 可以构造成功、失败、超时和缺少字段等不同场景。
- 保证测试不依赖外部 trace 和长时间运行。

### 9.3 集成测试

- 使用短 trace 运行至少两个真实预取器。
- 检查原始结果、解析结果、指标和图表是否连贯。
- 检查并行度 1 和并行度 4 的结果是否一致。
- 检查没有预取效果的场景是否得到合理解释。

### 9.4 指标正确性验证

对新增指标进行构造式测试：

- 合成一个只发生命中的 trace。
- 合成一个稳定 stride 的 trace。
- 合成一个完全无用预取的场景。
- 合成一个预取迟到但仍命中的场景。
- 人工计算期望值，与程序输出比较。

## 10. 实验效果评价

本项目至少应分别评价两类效果：

### 10.1 平台效果

- 批量实验总 wall-clock 时间。
- 并行度提升带来的吞吐率变化。
- 手工比较步骤减少情况。
- 失败任务是否能够被定位和重跑。
- 最终报告是否能从实验定义自动生成。

### 10.2 硬件研究效果

- 不同预取器的 IPC、MPKI、准确率和覆盖率差异。
- 不同 trace 下方案是否稳定。
- 新增指标是否解释了原有指标无法解释的现象。
- 同一预取器多次运行是否稳定。
- 结论是否能够从原始数据和配置回溯。

建议示例验收标准：

- 同一实验在并行度 1 和 4 下结果一致。
- 至少完成 3 个预取器、5 条 trace 和 3 次重复。
- 至少实现 2 个新增或派生的研究指标。
- 至少生成 3 类图表和一份自动 HTML/Markdown 报告。
- 任一图表都能回溯到 `run_id`、trace、配置和原始 JSON。
- 优化或新增功能具有单元测试和端到端测试。

## 12. 推荐技术实现

可以采用 C++ 和 Python 混合实现：

- ChampSim 侧：C++ 增加结构化统计记录和必要埋点。
- 实验平台侧：Python 3 实现实验编排、解析、指标和绘图。
- 两者之间：使用 JSON/JSONL 作为稳定接口。

也可以全部使用 C++ 实现实验平台，但需要额外引入 JSON、绘图和进程管理依赖。课程设计应优先保证对象模型和接口边界清晰，而不是追求复杂技术栈。

不建议把自定义指标直接拼接到非结构化文本中，再由正则表达式解析。结构化输出能减少格式变化带来的错误，也更方便单元测试。

## 15. 风险与范围控制

| 风险 | 影响 | 控制方法 |
| --- | --- | --- |
| 一开始就想做完整平台 | 无法按时完成 | 先完成最小闭环，再扩指标和图表 |
| 只画图不建立结果模型 | 不符合 OOP 重点 | 先设计 `RunResult` 和 `ResultSet` |
| 从文本中抓统计 | 易随格式变化失效 | 优先读取 ChampSim JSON |
| 自定义指标定义不清 | 研究结论不可信 | 写公式、单位、scope 和测试用例 |
| 无界并行 | 机器资源耗尽 | 使用有界调度器和资源限制 |
| 并行运行结果不同 | 无法复现 | 每个任务独立目录，结果按 `run_id` 管理 |
| 多预取器共享缓存被当作公平比较 | 结论错误 | 独立运行做公平对比，交互场景单独说明 |
| 只保留成功结果 | 缺少工程过程证据 | 记录失败任务、原因和修正方式 |
